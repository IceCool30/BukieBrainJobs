# Content Density and Decision Architecture

## Purpose

Use this reference whenever a BukieBrainJobs page, screen, component, flow, or customer-facing copy feels crowded, generic, repetitive, difficult to scan, or unclear about the next action.

The approved Task 1 refinement established a permanent product rule:

> Retain operational content. Remove promotional repetition.

This rule applies across the whole product. It does not mean removing useful detail. It means placing real detail at the decision point where it helps a Customer or BrainWorker act with confidence.

## The Decision Test

Review every visible heading, supporting line, badge, statistic, image, proof point, reassurance, price cue, CTA, label, and notification.

| Question | Keep when the answer is yes | Act when the answer is no |
|---|---|---|
| Does it explain the current task or state? | It clarifies what is happening now. | Remove it or replace it with a clearer state. |
| Does it help a person compare, choose, complete, recover, or comply? | It supports a real decision or required step. | Defer it until the relevant point in the journey. |
| Is it legally, operationally, or accessibly required? | It protects a person or makes the flow usable. | Consolidate it with related information or remove it. |
| Is it specific, true, and implemented? | It accurately describes product behaviour. | Remove it, flag it, or seek product confirmation. |
| Does it answer what this means, why it matters now, and what happens next? | It guides meaningful action. | Rewrite it or remove it. |

## The Five Outcomes

Every reviewed element should have one outcome.

| Outcome | Use when | Example |
|---|---|---|
| Retain | The element supports the current task or a required decision. | A clear price range near a booking action when the product can calculate it. |
| Consolidate | Several elements make the same point. | Replace a title, eyebrow, and generic subtitle with one clear heading and a short supporting line only where needed. |
| Defer | The information is useful later, but not for the current decision. | Show detailed payment explanation within booking rather than above service discovery. |
| Link | The information is real and needs depth, but does not belong inline. | Link from a concise support card to the relevant help or policy page. |
| Remove | The element is generic, repetitive, decorative, unsupported, or distracts from the task. | Remove a service-card tagline when the image, title, price cue, and destination already explain the choice. |

## Screen-Level Hierarchy

Start every screen with the primary task, then add only the supporting information that earns a place.

| Screen type | Lead with | Add only when it changes a decision |
|---|---|---|
| Public page | A clear marketplace route, value, or action | Relevant service context, truthful proof, and a useful secondary route |
| Search and discovery | Search, results, location relevance, or a service category | Filters, price cues, availability, and supporting detail required to compare options |
| Booking | Scope, selected service or BrainWorker, schedule, location, price, and payment state | Verification, escrow, cancellation, privacy, or support detail at the precise point it matters |
| Job posting | Job requirements, required fields, posting state, and next step | Advanced preferences or matching detail after the essential request is clear |
| BrainWorker profile | Relevant skills, service context, profile information, and booking path | Additional proof only when it is real, implemented, and useful to the booking decision |
| Onboarding | Current completion step, why it matters, and the next action | Deeper guidance or support after a person needs it |
| Customer or BrainWorker area | Current task, state, and next action | Context that helps complete, review, recover, or manage that task |
| Support or enterprise | The person’s route to resolution or contact | Precise capability detail that is relevant to the stated need |

## Copy and Heading Rules

A heading should establish a clear purpose. A supporting line should add information that the heading cannot carry alone. A CTA should name the action that follows. Do not create a stack of eyebrow, title, subtitle, reassurance, and CTA unless each layer changes a real decision.

| Pattern | Preferred use | Avoid |
|---|---|---|
| Heading | Name the task, decision, or outcome. | Decorative labels such as “Everything you need” or “Designed for you.” |
| Supporting line | Add a short, concrete clarification only when useful. | Repeating the heading with vague benefit language. |
| CTA | Use an explicit action verb. | Generic actions such as “Click here” or “Learn more” without a useful destination label. |
| Trust language | State an implemented product behaviour at the relevant decision point. | Repeating broad safety, escrow, availability, or verification assurances across a page. |
| Empty or error state | Explain what happened and the available recovery path. | Vague messages that give no next step. |
| Status | Show a real, current product state only when it changes the next action. | Decorative status strips and ambient availability wording. |

## Progressive Disclosure

Use progressive disclosure to protect the primary task without concealing required information.

1. Show the essential action and decision information first.
2. Reveal advanced options after a person reaches the relevant step.
3. Place complex explanation beside the choice it explains.
4. Link to deeper policies, help, or legal content when the person needs full detail.
5. Preserve accessibility, keyboard access, and clear state communication when detail is disclosed.

Do not hide pricing, material terms, required consent, destructive consequences, material availability limits, or recovery information merely to make a screen appear minimal.

## Platform Adaptation

Desktop can hold richer context when it supports a decision. Mobile should surface the immediate task and defer nonessential explanation. A mobile screen is not successful because it contains every desktop section at a smaller size. It is successful when a Customer or BrainWorker can complete the core task without distraction, clipping, or unnecessary scrolling.

For the homepage, follow the mobile and desktop composition rules in `live-approved-experience.md`. For every other screen, use the same product qualities and apply this decision test to the screen’s actual task.

## Review Prompts

Use these prompts during a design or content review:

- What is the one action this screen exists to support?
- Which information changes that action, and which information merely describes the brand again?
- Does the person need this detail now, later in the flow, or on a deeper page?
- Is the message true, implemented, and specific enough to trust?
- Can a keyboard user, touch user, or person using larger text reach and understand the same information?
- Would removing this element make the task less clear or less safe? If not, remove it.

## Examples From the Approved Product

A service card does not need a generic tagline when its photo, concise title, contained starting-price cue, and destination explain the task. A booking flow may need a precise escrow or privacy explanation because that information changes a payment or arrival decision. A mobile homepage should not duplicate desktop testimonials, calculator, profile, and FAQ sections when search and service discovery are the immediate jobs.

Use these examples as reasoning patterns, not layouts to duplicate.
