# ARCH-002 Contract Decisions

**Status:** Approved
**Date:** September 10, 2026
**Authority:** ARCH-002 Production-First Mock-Data Development Model

## Purpose

Record the delegated product and domain decisions needed to preserve production continuity while the frontend is developed with mock data.

## Decisions

### 1. Customer Budget and Worker Rate

A customer creating an open job request must not be required to provide `taskerRateKobo`. A worker rate is a marketplace pricing value that becomes authoritative only when sufficient worker, service, and pricing information exists.

Customer-created job input must therefore distinguish customer budget information from the eventual worker rate. The system must not use `0` as a fabricated worker rate.

The existing production `CreateJobRequest` remains authoritative for its current production use. A customer-facing creation contract should represent customer-known inputs and be transformed into a production job request only after required pricing and location resolution are available.

### 2. "I'm Not Sure" Skills

A customer may submit a job without selecting a specific skill when using the "I'm not sure" path.

The customer creation contract must allow an empty set of customer-selected skill IDs. This does not mean the production Job has no skill requirements. Skill resolution may occur later through category, job classification, matching, or another approved marketplace process.

No fabricated generic skill ID should be inserted solely to satisfy a required array.

### 3. Durable Customer Reference Code

A human-readable customer reference code is approved as a first-class production Job identifier in addition to the technical UUID primary key.

The reference code must be:

- unique
- durable across the Job lifecycle
- safe for customer-facing activity and support communication
- unsuitable as a replacement for the UUID primary key
- generated by the authoritative application/domain layer, not by presentation components

The exact Prisma migration and reference-code format are implementation work and must be reconciled with the current schema location before modification.

## Resulting Contract Boundary

```text
Customer Job Creation Input
  ├── title
  ├── description
  ├── job type
  ├── address/city/landmark
  ├── schedule
  ├── optional customer budget
  └── optional selected skills
              ↓
     validation + location resolution
              ↓
     marketplace/domain resolution
              ↓
       production Job request
              ↓
   PostgreSQL / Prisma persistence
```

## Implementation Rules

1. Do not weaken the existing production `CreateJobRequest` merely to accommodate incomplete customer knowledge.
2. Do not fabricate `taskerRateKobo`, coordinates, or skill IDs.
3. Do not allow UI presentation types to become the authoritative persistence model.
4. Keep monetary values as integer kobo in domain contracts.
5. Generate reference codes outside presentation components.
6. Before any Prisma migration, locate and inspect the actual current schema and verify the Job model.
7. Existing mock repositories must implement the same conceptual boundary so replacing the mock adapter with an API adapter does not require a UX redesign.

## Decision Status

All three delegated reconciliation decisions are settled. Remaining work is implementation of the approved contract boundary and database change, subject to normal branch, test, review, and Vercel verification gates.
